# 佐古研究室 卒業論文の書き方ガイド

初めて卒論を書く人向けの簡潔なまとめです。過去の卒論に共通する書き方を一般化したもので、公式の基準ではなく「慣行」として読んでください。

## 1. 全体像
- 分量は本文30〜40ページ前後（多くは26〜47ページ）。日本語で、「である調」、句読点は「，」「．」で統一します。
- LaTeXで組版し、目次・図目次・表目次を付けます。
- 流れは **問題の特定 → 評価軸（要件）の設定 → 提案 → 評価 → 考察 → まとめ** です。

## 2. 構成テンプレート
```
表紙（年度・和題・英題・指導教員・学科・学籍番号・氏名）
概要
目次／図目次／表目次
1 はじめに   1.1 研究背景（と目的）  1.2 貢献  1.3 論文構成
2 背景（用語・技術・制度）
3 既存手法・現状の整理（ここで「何が足りないか」を特定）
4 （要件定義→）提案
5 評価（要件充足／実験／比較／証明のいずれか）
6 考察・今後の展望
7 まとめ
謝辞
参考文献
付録（実装詳細・UI・成果物など）
```
章の数は内容に応じて増減してかまいません。ただし「1章の3節構成」と「まとめ」は必ず置きます。

## 3. 各部分の書き方

### 概要（10〜15行・1段落）
**背景 → 問題 → 既存の限界 → アプローチ → 結果・結論** の順に書きます。提案の説明で終わらず、結果（数値や結論）まで書きます。

### 1章 はじめに
- **1.1 背景**：課題を、日本の状況・具体データ・事例で示します。
- **1.2 貢献**：「〜を整理した」「〜を提案した」「〜を示した」のように、動詞を明確にして箇条書き（2〜5点）にします。各貢献が後の章の評価に対応するようにします。
- **1.3 構成**：「第2章では…」と、全章を漏れなく予告します。

### 背景・先行研究・現状整理
- 後続の理解に必要な範囲に絞ります（技術解説を書きすぎない）。
- 既存手法や資料の**不足点を特定**します。番号付きで列挙し、提案がそれに応える形にすると強くなります。
- 出典は一次情報（法令・RFC・国際標準・原論文・公的文書）を優先します。Webは [Accessed 日付] を付けます。

### 要件・評価軸
- 評価の基準を、**提案を読む前に**定義します。根拠（法令・標準・先行研究）を添えます。
- 基準は「満たす／一部満たす／満たさない」を判定できる形にします。

### 提案
- 課題と提案要素の対応を、図や表で追えるようにします。
- 自作の用語・記号・方式名は定義し、一貫して使います。
- フロー図、パラメータ表、擬似コードを使います。重い場合は付録に回します。
- 前提と射程を明示します（例：「最適であると主張するものではない」）。脚注で補足します。
- 提案の既知の欠点は、提案の章の中で先に開示します。

### 評価
手段は提案の性質に合わせて選びます。

| 手段 | 使いどころ |
|---|---|
| 要件充足性の比較表 | 制度・方式・プロトコルの提案 |
| ユーザ実験 | 使われ方が問われるシステム |
| 性能比較 | 実装・アルゴリズム |
| 安全性・正当性の証明 | 暗号・分散システム |
| 後から公開された公的資料との突合 | 実務向けの手順・マニュアル |

- 比較対象と指標を事前に明示します。
- 実験は 目的 → 環境・参加者 → 事前チェック項目 → 手順 → 結果 の順に書きます。
- **不利な結果も隠さず**、トレードオフや知見として考察します。
- 小規模な実験の限界を書き、結論を一般化しすぎません。

### 考察・今後の課題
- 結果の意味（なぜそうなったか、何が分かったか）を述べます。
- 本研究の範囲外の課題は、はっきり切り分けます。
- 今後の課題は「何を・どうやって」まで具体的に書きます。

### まとめ
貢献の各項目に対応する結論を書きます。概要・貢献・まとめで、同じ骨格・同じ用語を使います。新しい情報はここで初出にしません。

### 謝辞
定型は「指導教員の佐古教授には多くのご指導ご鞭撻を賜りました．…早稲田大学佐古研究室の皆様にも，内容に関する議論や，論文のチェックなど…」です。助言をもらった外部の方がいれば、所属や氏名を添えます。

## 4. 良い卒論の共通点
1. 問い・評価軸・貢献が、概要・1章・評価・まとめで一貫している。
2. 既存の不足点を特定し、提案がそれに対応している。
3. 比較対象と評価の物差しが明確である。
4. 表と図で整理している（一覧表、要件対応表、比較表、フロー図）。
5. 主張の強さが評価の強さと釣り合っている。未検証の点は未検証と書く。
6. 限界と今後の課題を自分で書いている。

## 5. 避けたい点
- 概要が提案の説明で終わり、結果が書かれていない。
- まとめが数行で、貢献との対応が見えない。
- 評価が「今後の課題」だけで、有効性が未検証である。
- 評価環境や実験規模が小さいのに、結論が一般的すぎる。
- 背景の技術解説が長く、提案の説明が薄い。
- 用語・略称が初出で定義されていない。

## 6. 提出前チェック
- [ ] 概要・1.2貢献・まとめの対応が取れている
- [ ] 全章が1.3で予告され、章末の内容と一致している
- [ ] 評価軸が提案より前に定義されている
- [ ] 数値が本文・図表・まとめで一致している
- [ ] 図表に番号・キャプションがあり、本文から参照している
- [ ] 参考文献の書式が統一され、Webにはアクセス日がある
- [ ] 略称は初出で定義している
- [ ] 「である調」と句読点が統一されている
- [ ] 研究室メンバーに査読してもらった
- [ ] 個人情報・実験参加者の扱い・生成AIの利用ルールを確認した
