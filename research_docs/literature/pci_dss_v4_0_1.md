## 2. 主張（読んだ範囲。【文献】）

### 2.1 誰に適用されるか（p.5）

- 【文献】PCI DSS は、カード会員データ（CHD）や機密認証データ（SAD）を保存・処理・伝送するすべての事業体と、その環境のセキュリティに影響し得るすべての事業体が対象。加盟店、プロセサー、アクワイアラ、イシュア、その他のサービスプロバイダを含む。
- 【文献】事業体が PCI DSS への準拠または準拠の検証を必要とするかは、**準拠プログラムを管理する組織（ペイメントブランドやアクワイアラなど）の判断**で決まる。
- 【未確認】日本の法令（割賦販売法など）や「非保持化」との関係は、この文書の読んだ範囲にない。

### 2.2 要件 6.4.3: 決済ページのスクリプトの管理（p.185〜187）

- 【文献】消費者のブラウザに読み込まれ実行されるすべての決済ページスクリプトを、次のように管理する。①各スクリプトが認可されていることを確認する方法、②各スクリプトの整合性を保証する方法、③すべてのスクリプトのインベントリ（それぞれが必要な理由の、ビジネス上または技術上の正当性の文書つき）。
- 【文献】適用範囲: 事業体の環境、サードパーティ、第4のパーティからロードされるすべてのスクリプト。**TPSP/支払処理業者の埋め込み決済ページ/フォーム（iframe など）を含む事業体の Web ページ内のスクリプトにも適用される。** 一方、TPSP/支払処理業者の埋め込みフォーム（iframe）の**中**のスクリプトは、事業体ではなく TPSP/支払処理業者が管理する責任がある。
- 【文献】整合性を強制するメカニズムの例（ガイダンス）: サブリソースの整合性（SRI）、コンテンツセキュリティポリシー（CSP）、独自のスクリプトまたはタグ管理システムなど（これらに限定されない）。
- 【文献】グッドプラクティス: 決済ページを iframe に読み込む場合、親ページの CSP で決済ページを読み込める場所を制限すると、未承認コンテンツが決済ページに置き換えられることを防げる。
- 【文献】この要件は 2025 年 3 月 31 日まではベストプラクティスで、それ以降は必須。

### 2.3 要件 11.6.1: 変更・改ざん検知（p.334〜336）

- 【文献】消費者ブラウザが受け取る、セキュリティに影響する HTTP ヘッダーと決済ページのスクリプトの、不正な変更（侵害の指標、変更、追加、削除を含む）を、担当者に警告するメカニズムを展開する。実行頻度は、少なくとも7日に1回、または、ターゲットリスク分析（要件 12.3.1）で定めた頻度。
- 【文献】ガイダンス: 悪意のある活動による変更や指標を検出する「唯一の場所は、ページが構築され、すべての JavaScript が解釈される消費者ブラウザの中」。受け取った HTTP ヘッダーと決済ページを、以前の版や既知の版と比べて検出する。既知の侵害の指標や、スキマーに典型的なスクリプト要素・動作を探して警告する方法も挙げる。
- 【文献】メカニズムの例（p.336）: CSP 違反の報告（`report-to`、`report-uri`）、CSP 自体の変更の検知、受け取った Web ページを要求・解析するシステムによる外部監視（合成ユーザ監視）など。
- 【文献】**適用上の注意: この要件の意図は、事業者が消費者のシステムやブラウザにソフトウェアをインストールすることではなく、事業者が上の例のような技術で、予期しないスクリプト活動を防止・検出すること。**
- 【文献】この要件も、2025 年 3 月 31 日まではベストプラクティスで、それ以降は必須（p.335 の注記）。

### 2.4 要件 4.2.1、3.3.1.2（自作 EC が要件に入れていないセキュリティ管理の例）

- 【文献】4.2.1（p.139）: オープンな公共ネットワークでの送信時に、強力な暗号とセキュリティプロトコルで PAN を保護する。信頼できる鍵と証明書だけを受け付ける。証明書は有効で、期限切れや失効がないことを確認する。
- 【文献】3.3.1.2（p.101）: オーソリゼーションプロセスの完了時に、カード検証コードを保持しない。

## 3. 本研究との関係

- 【決定】自作 EC は、「PCI DSS に準拠した EC」ではない。送信の経路に関わる性質だけを再現し、TLS・保存禁止・アクセス制御などは要件に入れない（`../experiment_spec.md` §3.1、§3.5。D15）。2.4 の 4.2.1・3.3.1.2 は、その例にあたる。
- 【文献】6.4.3 と 11.6.1 は、**加盟店側が、決済ページのスクリプトを管理・監視する**要求。自作 EC は、CSP、SRI、スクリプトのインベントリ、改ざん検知のどれも再現していない。EC 側の防御がある環境で、スキマーの成立や拡張機能の観測がどう変わるかは、本研究では測っていない（【未確認】）。
- 【解釈】11.6.1 の注意事項（消費者のブラウザへのソフトウェアのインストールを意図しない）から、本研究が測る**消費者側の拡張機能は、PCI DSS が事業者に求める対策とは別の層**にある。「PCI DSS が求めていない層の対策が、どこまで観測できるか」を測る、という位置づけが読める。ただし、PCI DSS が消費者側の対策を排除しているとは、文書から言えない。
- 【解釈】6.4.3 の iFrame の扱い（iframe の外の加盟店ページのスクリプトは加盟店の責任。親ページの CSP で置き換えを防ぐ）は、モデルY（iFrame を偽フォームに置き換える。D25）の脅威と対応する。
- 【解釈】11.6.1 の「唯一の場所は消費者ブラウザの中」は、本研究の問題意識（消費者側ブラウザでの観測）と近い。ただし、11.6.1 が求めるのは、事業者が消費者ブラウザ相当の環境で監視すること（合成ユーザ監視など）で、消費者自身の拡張機能ではない。
