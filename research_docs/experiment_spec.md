# 実験仕様書（実験環境の設計とテスト）

出典の略称は `README.md` を参照。決定は `research_decisions.md`（D、Q）、用語と観測レベルは `observation_model.md`。
**状態: §1〜§8、§10、§11 は記述済み。§9 は未確定事項の一覧で、XHR の扱いなどが残る。**

この文書の目的は、実験環境（EC、スキマー、拡張機能）が「要件を満たしているか」「正しく実装できているか」を、コードを見せずに、理由をもって説明できるようにすることです（D22）。

## 1. 全体像

### 1.1 何を測る実験か

消費者のブラウザに入れた拡張機能（Chrome の MV3）が、ECサイトの決済でカード情報が送られる様子を、どこまで見て判定できるかを測ります。そのために、自分の PC の中に、次のものを全部自作して動かします。（D12、D13）

| 部品 | 何か | 本物との関係 |
|---|---|---|
| **EC** | 決済ページを持つ店のサイト。PCI の5型のどれかで作る（D5） | 本物のECの代わり。「最も簡素な最低要件」で作る（D15） |
| **ダミーPSP** | カード情報を受け取って処理する決済代行の代わり | 本物の PSP（Stripe 等）の代わり。基本の実験はダミーPSPで行い、実 Stripe（テストモード）の版は別枠の追加実験（D12。2026-11-17 に変更） |
| **スキマー** | EC に不正に埋め込まれた JavaScript。入力されたカード情報を攻撃者へも送る | 公開レポート（RiskIQ）の挙動を自作する。本物の攻撃コードは使わない（D6、D7） |
| **sinkhole** | 攻撃者サーバーの代わりの受け手。自分の PC の中だけにある | スキマーの送信先（D13） |
| **拡張機能** | 測定される側の装置。案A（ページの中で `fetch` を横取り）と案B（`webRequest` で外側から監視）の2種類（D9） | 実際に消費者が入れる拡張機能の代わり |
| **正解記録** | 「実際に何が送られたか」の記録。拡張機能とは独立に取る（D18） | 拡張機能の結果を採点する基準 |

### 1.2 関係の簡略図

```
┌──────────────────────── 顧客のブラウザ ────────────────────────┐
│                                                                │
│  ┌──── EC の決済ページ（5型のどれか）────┐                    │
│  │                                        │                    │
│  │  カード入力欄 ──────(A)正規の送信────────────────▶ ダミーPSP │
│  │       │            （API型は加盟店サーバー経由）            │
│  │       │                                │                    │
│  │  ┌────▼─────────────┐                  │                    │
│  │  │ スキマー          │                  │                    │
│  │  │ 取得部: 入力を手に入れる              │                    │
│  │  │ 送信部: 手に入れたものを送る ──(B)悪性の送信───▶ sinkhole │
│  │  └──────────────────┘                  │                    │
│  └────────────────────────────────────────┘                    │
│                                                                │
│  拡張機能（案A: ページ内で横取り / 案B: webRequest で外側から）  │
│       │ (A) と (B) をどこまで見られたか                        │
└───────┼────────────────────────────────────────────────────────┘
        ▼
   観測結果（L1 発生 / L2 宛先 / L3 内容 / L4 判定）
        │
        ▼ 照合
   正解記録 ＝ サーバー受信ログ（ダミーPSP・sinkhole・加盟店サーバー）＋ CDP（ブラウザ側の通信記録）
        │
        ▼
   一致 → 「観測できた」／不一致 → 原因を3分類（①案Aの実装不足 ②MV3の構造的限界 ③ブラウザを通らない外縁）
```

- **(A) 正規の送信**: 顧客がカード情報を入力して「支払う」を押したときの、本来の送信。送り先は型によって違う（§1.4）。
- **(B) 悪性の送信**: スキマーが、入力されたカード情報を sinkhole へ送る送信。リダイレクト型では測定しない（D16）。
- **CDP**（Chrome DevTools Protocol）: ブラウザの外側から、ブラウザの動きと通信を記録できる仕組み。拡張機能とは別系統なので、採点の基準にできる。

### 1.3 1回の試行の流れ（例: iFrame型）

1. 顧客役の自動操作が、決済ページでテストカードを入力する。カード名義には、その試行だけの識別子を入れる（D20）。
2. 入力欄は PSP の iFrame の中にある。(A) 正規の送信が、iFrame からダミーPSPへ行く。
3. スキマーは、別オリジンの iFrame の中を直接読めない（SOP。PoC の E1 で確認）。そこで取得部が、偽フォームに置き換えて入力を手に入れ、送信部が (B) として sinkhole へ送る。
4. その後、本物の PSP の iFrame を出し直す（D25）。顧客役がもう一度入力し、(A) 正規の送信が、無改造の PSP の iFrame からダミーPSPへ行く。
5. 拡張機能が、(A)(B) を見る。見た結果を L1〜L4 で記録する。案Aと案Bは、別々の試行で測る（D40）。
6. 正解記録（受信ログと CDP）と照合する。識別子で、どの試行の記録かを結びつける。

【決定】偽フォームに置き換えた後は、本物のフォームを出し直す（D25）。理由は、正規送信が正規ケースと同じ経路になり、差の原因を悪性送信だけに絞れるため。RiskIQ 報告書の Group 4 は、置換後に決済を成立させるかを明記していない。

### 1.4 型ごとの違い

| 型 | カード入力欄の場所 | 正規の送信先（正規宛先。【仮説】PCI の経路からの導出） | スキマーの取得部（【決定】D31） | 悪性ケース |
|---|---|---|---|---|
| URLリダイレクト | PSP のページ | ダミーPSP | （なし） | 測定対象外。正規ケースのみ（D16） |
| iFrame | 加盟店ページ内の PSP の iFrame | ダミーPSP | 偽フォームに置換 | 測定する |
| ダイレクトポスト | 加盟店ページのフォーム | ダミーPSP | 入力欄を読む | 測定する |
| JavaScriptフォーム | PSP の JS が加盟店ページ内に作るフォーム | ダミーPSP | 入力欄を読む（E11 で読めた。自作の PSP の JS・各1回） | 測定する |
| API | 加盟店ページのフォーム | 加盟店サーバー | 入力欄を読む | 測定する。加盟店サーバー→PSP はブラウザ外で、見えない（外縁③） |

### 1.5 結果の見方

最終的に作る表は、行が「型 × 正規/悪性」、列が「観測点（案A、案B）× L1 発生 / L2 宛先 / L3 内容 / L4 判定」です（D40。`observation_model.md` §6）。リダイレクト型の悪性の行は「測定対象外」と書きます。

## 3. ECの設計と確認項目

### 3.1 設計の考え方

【決定】ECの最低要件は、**送信の経路に関わる性質だけ**を入れる（入力欄の場所、送信を出すもの、宛先、加盟店のシステムがカード情報を受け取るか）。理由: この研究が測るのは送信の観測で、TLS や保存禁止などのセキュリティ管理は測定項目に入らない。範囲を絞ると、要件ごとに PCI のページを付けられ、確認も自動化しやすい（D15）。

- 「PCI DSS に準拠したEC」とは主張しない。論文には「PCI の補足文書 [PCI §2.1〜2.5] が記述する送信経路を再現した」と書く。
- 要件1つにつき、確認の場所を決める（§3.2〜§3.4）。毎試行の自動チェック（§6.2）か、構造チェック（§6.4）で確かめる。わざと要件を破ったECで確かめる反例テストは行わない（D48）。
- 確かめる根拠は、加盟店サーバーの受信ログ、ダミーPSP の受信ログ、CDP の記録（D18）。

### 3.2 全型に共通する要件

| ID | 要件 | 根拠 | 確認の場所 |
|---|---|---|---|
| C1 | カード情報の最終的な受け手は PSP（ダミーPSP）である | 【文献】全型の手順の末尾（p.9、p.11、p.14、p.16、p.17-18） | 毎試行 #1 |
| C2 | 正規宛先は、送信ごとに1つである | 【決定】D17 | 毎試行 #2 |
| C3 | カード番号は公開テスト番号だけ。識別子はカード名義の欄に入れる | 【決定】D13、D20 | 毎試行 #5 |
| C4 | 正規送信には、全型で入力欄の全項目（CVC を含む）を含める | 【決定】D34 | 毎試行 #1 |

### 3.5 この節の限界

- 【決定】TLS、カード情報の保存禁止、アクセス制御などのセキュリティ管理は要件に入れない（§3.1）。
- 【決定】正規の送信が複数の宛先に出る流れ（3Dセキュア、トークン化用の別ホスト）は扱わない（D17）。
- JavaScriptフォーム型の PSP の JS は、ダミーPSP が配る自作の JS で再現する。基本の実験では、本物の PSP の JS は使わない（D12、D13）。実 Stripe の版は別枠の追加実験として作る（D12。2026-11-17 に変更）。【推奨を承認済み】
- 【決定】PCI §2 冒頭の一覧にある「iFrame以外のタグによる埋め込みコンテンツ」「加盟店ゲートウェイ + 第三者の埋め込みAPI」は範囲外（D43）。「PCI の5型を採用し、ほかの2項目は扱わない」と書き、PCI の分類を網羅したとは書かない。
- 【決定】実在のECの実態調査はしない（D45）。自作の5型が実在のECを代表するかは未検証で、限界・今後の課題に書く。
- 【決定】正規送信（顧客のカード送信）は、全型で `fetch` に統一する（D49）。リダイレクト型の加盟店→PSP のページ遷移は遷移のまま。フォーム送信は §10。論文には「正規送信は `fetch` に統一した」を限界として書く。
- 上の確認項目のうち、毎試行の自動チェックと構造チェックは、5型とも実装し、拡張機能なしの基準試行（E6〜E14）で実施した（各1回。構造チェックは全12項目が合格）。拡張機能の観測のテスト T1 は実装し、拡張機能ありの全54試行（E15・E16）で実施した（§6.5）。

## 4. スキマーの設計

### 4.1 設計の考え方

- 【決定】スキマーは、**取得部**（カード情報を手に入れる）と**送信部**（送信手段・宛先・符号化）に分けて作る。送信部は全モデルで共通（D23）。理由: 観測結果の差の原因を特定するため。送信部が共通なら、差は「EC型の違い」か「取得部の違い」による、と説明できる。
- 【決定】モデルは2つ。取得部の方法で分ける（D26）。
- 【決定】本物の攻撃コードは使わない。RiskIQ が記述した挙動を、自作で再現する（D6、D7）。
- 【限界】この検体は、本物のスキマーそのものではない。主張できる範囲は「[RQ] が記述した取得・送信の挙動を再現した」までで、「実在のスキマー全体を代表する」とは書かない。

### 4.2 2つのモデルと型ごとの当てはめ

| | モデルX | モデルY |
|---|---|---|
| 取得部の方法 | 入力欄の値を読む | 決済フォームを偽フォームに置き換える |
| 基にするグループ（D27） | Group 5（全入力欄の name と value を取得、ボタン・フォームにイベントを付ける。【文献】p.19-31） | Group 4（決済フォームを偽フォームに置き換える（オーバーレイ）。【文献】p.16-17） |
| 埋め込む型（D31） | ダイレクトポスト、JavaScriptフォーム、API | iFrame |
| リダイレクト型 | 埋め込まない（悪性ケースは測定対象外。D16） | 埋め込まない |

- モデルY の流れ（D25）: 偽フォームで入力を取得して sinkhole へ送る → 本物の PSP の iFrame を出し直す → 顧客役がもう一度入力 → 正規送信は無改造の iFrame から出る。流れの全体は §1.3。
- JavaScriptフォーム型のフォームは、通常の DOM 要素で作る（Shadow DOM・iFrame は使わない。D31）。入力欄をモデルXが読めることは、E11 で確認した（【観測】。自作の PSP の JS・各1回。F15）。実在のPSPの JS では【未確認】。
- API型の悪性ケースは、ブラウザ側のスキミングだけを測定する。サーバー側スキミングは測定対象外（D31）。入力欄をモデルXが読めることは、E13 で確認した（【観測】。自作EC・各1回。F16）。

## 5. 観測点・正解記録・識別子の設計

### 5.1 正解記録

正解記録は、拡張機能の判定が合っているかを調べるための基準で、拡張機能とは別の手段で「実際に何が送られたか」を記録したものです。サーバー受信ログと CDP（Chrome DevTools Protocol。ブラウザの通信を外から観察する仕組み）の2本立てとします（【決定】D18）。以下の記録項目は【提案】を研究者が了承したもの（2026-11-03）。

**(1) 受信ログ（ダミーPSP、sinkhole、加盟店サーバーの3か所）**

| 項目 | 目的 |
|---|---|
| 実行ID（試行ごとに振る） | 拡張機能の結果と突き合わせる |
| 受信時刻 | 順序の確認（S3 など） |
| 受信したサーバー名 | L2（宛先）の正解 |
| メソッド・パス | 同上 |
| `Origin` / `Referer` ヘッダ | 送信元ページの確認 |
| 本文の全項目（CVC を含む） | L3（内容）の正解。C4・S5 の検証 |
| 識別子（氏名欄。D20） | 試行の取り違え防止 |

理由: L1（発生）は届いたか、L2 は届いた先、L3 は届いた内容で、受信ログだけで正解が決まる。本文は加工せず全文を残す。

**(2) CDP（ブラウザ側）**

| 項目 | 目的 |
|---|---|
| 発信元フレーム（frameId、フレームの URL） | iFrame 内から送ったか、親ページから送ったかの正解 |
| 宛先 URL、メソッド、本文 | 受信ログとの突き合わせ |
| 送信 API の種別（fetch / XHR） | D28 の検証 |

理由: 受信ログからは発信元フレームが分からない。iFrame 型では、iFrame の中から送ったか、親ページから送ったかを区別する正解が要る。ブラウザは送ったがサーバーに届かなかった場合は、受信ログに残らない。

**2本の突き合わせ**: 両者の記録の一致を確認する（D24 の正解記録の検証。§6.5）。

【観測】CDP の本文は、WSL2 上の Playwright 同梱 Chromium 158 で、`fetch` の POST（`application/x-www-form-urlencoded`、同一セッションのトップフレーム）では、`D-N-OX-001`・`D-M-OX-001` の全 POST（3件）で取れた（`Network.requestWillBeSent` の `postData`。`product/NOTES_assumptions.md` #26、#28）。別オリジン iFrame・他の型・他の送信手段では未確認で、T2 の検証項目として条件ごとに取得率を記録し続ける。

### 5.2 識別子と記録の結びつけ

PAN は公開テスト番号で同じ値が繰り返し出る（D20）ので、PAN では試行を区別できない。また、拡張機能が内容（L3）を読めなかった試行では、拡張機能の記録に識別子が残らない。識別子だけを鍵にすると、観測できなかった試行ほど突き合わせができなくなる。以下は【提案】を研究者が了承したもの（2026-11-03）。

**(1) 識別子の形式**
- `ID-<実行ID>-<乱数4桁>`（例: `ID-I-M-OA-003-K7Q4`）。氏名欄に入れる（D20）。条件ID・実行ID の書式は次のとおり（【決定】D41）。
  - 条件ID = `<型>-<正規/悪性>-<観測点>`。型は `R`（リダイレクト）、`I`（iFrame）、`D`（ダイレクトポスト）、`J`（JavaScriptフォーム）、`A`（API）。正規/悪性は `N`/`M`。観測点は `OA`（案A）/`OB`（案B）/`OX`（拡張機能なしの基準試行。§6.3）。例 `I-M-OA`。`R-M-*` は作らない。測定の条件は18、基準試行は9。
  - 実行ID = `<条件ID>-<試行番号3桁>`（例 `I-M-OA-003`）。試行番号は、無効試行も含めて、その条件の試行を始めた順の通し番号。
  - 拡張機能の設定は1通りに固定する（D42）ので、条件ID に設定の印は付けない。
- 英大文字・数字・ハイフンだけで作る（氏名欄の入力制限で弾かれにくくするため）。
- 乱数部分は、記録したシードから生成する（再現できる。§7）。
- 理由: 実行ID（条件ID と試行番号）で、ログを人が見て何の試行か分かる。通し番号にするのは、無効試行の再実行（D24）で番号を使い回さないため。乱数部分は、別の試行の値との偶然の一致を避ける。

**(2) 結びつけの鍵は2本立て**

| 鍵 | 内容 | 役割 |
|---|---|---|
| 実行ID | 測定スクリプトが試行ごとに振り、開始・終了時刻と条件を記録する | 主キー。3つの記録（受信ログ、CDP、拡張機能）を、この時間帯に入るものとして結びつける。拡張機能が内容を読めなくても結びつけられる |
| 識別子（氏名欄） | 本文に入る値 | 照合用。主キーでの結びつけが正しいかの確認と、想定外の宛先に識別子が現れる経路の漏れの検出 |

【未確認】試行間の時間帯の区切り方（前の試行の遅延送信が次の試行に混ざらないための待ち時間）は、実装後に確かめる。§7 で扱う。

### 6.5 拡張機能の観測のテスト

【観測】T1 は `product/harness/t1.js` で実装し、拡張機能ありの全54試行（E15・E16）で実施した。全試行・全レベルで、全ての送信が一致した（見逃し0、誤検出0、内容の誤り0）。T2 は毎試行チェックの #T2 として全試行で合格した。T1 の不一致は結果であり、試行を無効にしない（無効にするのは毎試行チェックと T2 の不合格）。

拡張機能の結果が間違う仕方は3つある。見逃し（実際に送られたのに記録しない）、誤検出（送られていないのに記録する）、内容の誤り（宛先や本文が実際と違って記録される）。以下は【提案】を研究者が了承したもの（2026-11-03）。

| テスト | 内容 | 根拠 |
|---|---|---|
| T1 一致テスト | 試行ごとに、拡張機能の記録と正解記録（§5.1）を実行ID（§5.2）で突き合わせ、見逃し・誤検出・内容の誤りを数えて報告する | 見逃しが正解記録で数えられれば、「観測できない」という結論が実装不足によるものかを切り分ける材料になる |
| T2 正解記録の検証 | 受信ログと CDP が食い違った試行は、無効として記録し、捨てずに報告する（D24）。あわせて、CDP が本文を取れた試行の割合を条件ごとに記録する。取れない条件は、受信ログだけを正解にし、その旨を結果に書く【提案。研究者が承認 2026-11-10】 | 模範解答が間違っていれば採点が無意味になる。CDP が本文を取れる範囲は実装して確かめる（§5.1） |

**実装不足と構造的限界の切り分け（【決定】D35）**: 観測できなかった条件は、同じ条件で実装を直して（注入タイミングを変える等）再試行する。直して観測できれば①実装不足、直しても観測できなければ②MV3の構造的限界とする。再試行の前は「分類未了」と書く。③ブラウザを通らない外縁は、この手順の対象外（正解記録の受信ログにのみ現れる送信）。

## 7. 試行方針と結果の記録形式

### 7.1 試行ごとに保存する項目

第三者が同じ結果を再現できるかという問いに答えるため、1回の試行ごとに次を保存する。以下は【提案】を研究者が了承したもの（2026-11-03）。生のログを残せば、集計方法を後から変えても再計算できる。

| 項目 | 目的 |
|---|---|
| 実行ID、条件ID、試行番号、開始・終了時刻 | 記録の結びつけ（§5.2） |
| 識別子と、その乱数シード | 同じ値の再現 |
| Chrome のバージョン | ブラウザ側の挙動の違いを区別する |
| 拡張機能のハッシュ（ビルド済みファイルの SHA-256）と設定（`all_frames`、world） | どの版で測ったかの特定 |
| スキマー検体のハッシュ | 同上 |
| 受信ログ、CDP の記録、拡張機能の記録（生のまま） | 後から再集計できる |
| 試行の有効/無効と、無効の理由（毎試行チェックの不合格、T2 の食い違い等） | 無効試行を捨てずに報告する（D24） |

**保存場所と形式【決定】D39**: リポジトリ直下の `expt_log/`。第1層が条件ID、その中に試行ごとのフォルダ（実行IDで命名）。

```
expt_log/
└─ <条件ID>/
   └─ <実行ID>/
      ├─ meta.json              条件ID、試行番号、時刻、識別子、シード、Chrome のバージョン、各ハッシュ、有効/無効と理由
      ├─ receive_<サーバー名>.jsonl   受信ログ（ダミーPSP、sinkhole、加盟店サーバー。サーバーごと）
      ├─ cdp.jsonl              CDP の記録
      └─ extension.jsonl        拡張機能の記録
```

- 生ログは1行1記録（JSON Lines）で、加工せずに残す。
- 案Aと案Bは別々の試行で測る（D40）。条件ID に観測点（A/B）を含め、`extension.jsonl` はその試行の観測点1つだけを記録する。

- 条件ID・実行ID の書式は §5.2（D41）。例: `expt_log/I-M-OA/I-M-OA-003/`。
- 公開は GitHub（D19。検体コードを含めてすべて公開。限定公開）。

### 7.2 試行回数

基本3回、食い違いが出た条件だけ10回（【決定】D21。2026-11-16 に20回から変更）。以下は運用の【提案】を研究者が了承したもの（2026-11-10）。

**食い違いの2種類**（どちらかが出た条件を10回に増やす）
1. 試行間の食い違い: 同じ条件の3回で、結果（L1〜L4 の到達度）が揃わない（例: 2/3）。
2. 拡張機能と正解記録の食い違い: T1 一致テストで、見逃し・誤検出・内容の誤りが1回でもある。

**その他の約束**
- 10回の結果は「8/10」のように生の値で報告する。食い違いは結果として記録し、捨てない（D21）。
- 3回すべて一致した条件でも、「常に観測できる」とは書かない（D21）。
- 無効試行（毎試行チェックの不合格、T2 の食い違い）は回数に入れず、有効な試行で3回（または10回）に達するまで再実行する。無効試行の記録は残す（D24）。

理由: 2種類を含めると、毎回同じように失敗する場合（構造的な限界の可能性）と、ときどき失敗する場合（タイミングや Service Worker の停止などの不安定さ）の、どちらも拾える。

## 11. 実装方針

D53〜D56 の要約と、実行環境（2026-11-12 に研究者が選択。D番号は付けていない）。

- **置き場所**: このリポジトリの `product/`（D53）。サブフォルダは `merchant/`、`psp/`、`sinkhole/`、`skimmer/`、`extension/`、`harness/` を想定。実験ログは `expt_log/`（D39）。
- **技術**: Node.js + 素の JavaScript。測定の自動化は Playwright。ビルド工程は入れない（拡張機能のハッシュは、書いたファイルそのもの）。最初に小さく試した細部の結果は、`product/NOTES_assumptions.md` #3〜#7、#13〜#16（`*.localhost` の名前解決、別オリジン iFrame の CDP 記録、拡張機能の読み込みは実測済み。実験の環境でのスパイクは1回ずつ）。実験の試行は `product/harness/run_trial.js` で行い、記録は `expt_log/` に置く。
- **実行環境**: WSL2（Ubuntu）上で、Playwright 1.65.0 同梱の Chromium（158.0.8127.18）を使う。起動は `channel: 'chromium'`（フル版の Chromium。新 headless）を必ず指定する。【観測】指定しない `headless: true` は Chrome Headless Shell を起動し、拡張機能が読み込まれず、別オリジン iFrame も別プロセス（OOPIF）にならなかった（`product/NOTES_assumptions.md` #14）。理由: ブラウザの版を Playwright の版で固定でき、自動更新で変わらない。Windows では Smart App Control が同梱 Chromium を未署名として止めた（同 #1、#11）。リポジトリは WSL の Linux 側に置く。実測は `product/NOTES_assumptions.md` #13〜#16。インストール済みの Chrome／Edge を使った Windows でのスパイク結果（#3〜#7）は、実験の環境ではない。
- **順序**: D → I → J → A → R（D56）。各型で、EC・検体・案A・受信ログ・基準試行を通して動かす縦切り。
- **スキマーが成立しない型**: 実装の誤りを直しても成立しなければ「測定対象外（スキマー不成立）」。第3モデルは置かない（D55）。
- **締切**: 2026年12月中（日付は【未確認】。D56）。
