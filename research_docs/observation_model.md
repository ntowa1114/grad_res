# 観測モデル・用語・評価基準

出典の略称は `README.md` を参照。決定済みの定義は主に [H §2-§5]。

## 1. 用語

| 用語 | 定義 | 出典 |
|---|---|---|
| スキマー | 正規ECサイトに不正に埋め込まれ、入力されたカード情報を攻撃者サーバーへ送る JavaScript。別名 Magecart / formjacking | [H §2] |
| PSP | 決済代行会社（例: Stripe, GMO）。カード情報を加盟店に代わって扱う | [H §2] |
| 加盟店 | PSP を使っているEC店舗 | [S P16] |
| PAN | カード番号（Primary Account Number） | [H §2] |
| MV3 | Manifest V3。Chrome拡張の現行仕様。通信のブロック能力が削られ、観測が中心 | [H §2] |
| 案A | ページ内で JavaScript の送信命令（fetch等）を横取りして中身を見る拡張方式 | [H §2] |
| 案B | webRequest でページ外側からネットワーク通信を監視する拡張方式 | [H §2] |
| allowlist | カード情報を送ってよい正規宛先のリスト | [H §2] |
| SOP | 同一オリジンポリシー。ページ JS 同士を隔てる仕組み | [S P18], [P 実験1] |
| 正解記録 | 観測装置と独立した記録（自前サーバーの受信ログ、将来は CDP 等）。測定対象ではなく照合用 | [H §5], [P 実験1] |
| overturn | [H §8] に「案Bのoverturn（iframe型でもL3観測可）」とある語。定義は資料にない。意味は【未確認】 | [H §8] |

## 2. 観測レベル（L1〜L4）

| レベル | 内容 | 現在の実装 |
|---|---|---|
| L1 発生 | カード送信が起きたことを検知 | 案A・案B（PoC） |
| L2 宛先 | 送信先を特定 | 案A・案B（PoC） |
| L3 内容 | 送信内容からPANを復元 | 案A・案B（PoC）。判定は素朴な `includes` のみ [P] |
| L4 判定 | allowlist 照合で正常/危険を判定 | 案Bのみ実装。案AのL4は未実施 [P] |

【未確認】L1〜L3 を「○/△/×」と判定する閾値、反復回数、「復元成功」の基準は未定義。[P] は「反復・到達率（○△×の量的判定）は未実施」としている。

## 3. 決済方式の分類

- 【決定】PCI の5型（URLリダイレクト / iFrame / ダイレクトポスト / JavaScriptフォーム / API）を決済方式の分類とする。2026-10-24 に研究者が決定（`research_decisions.md` C6）。定義は [PCI §2.1〜2.5, p.8-18]、発表資料での記載は [S P12, P21]。
- 変更前: 4分類（リダイレクト型 / iframe型 / JSトークン型 / 直接送信型）を分析の骨格とした。[H §3]（[H] 原本は4型のまま）
- 【未確認】旧4分類の名称と5型の対応（JSトークン型 = JavaScriptフォーム型か、直接送信型 = ダイレクトポスト型か等）は資料から判断できない（`analysis/open_issues.md` E-1）。
- 【観測】PoC の2方式は、直接送信型（トップから送信）、iframeホスト型（別オリジン iframe 内から送信）と呼ばれている。[P] 本実験用の実装はまだ無い（2026-10-24、研究者の申告）。

## 4. 観測点

- 【決定】観測点は案A・案Bの2点。理由は作業量ではなく、「ページ内側の層（案A）と外側の層（案B）の代表」であること。[H §5]
- 計測器（CDP等）は3点目だが、案A・案Bの結果を照合する正解記録として使う。測定の列は2点のまま。[H §5]
- 案Aの横取りは、検体の送信手段（軸1）と一致させる。[H §5]
- 【観測】案Aが成立する条件は MAIN world かつ iframe 内にも注入すること（`all_frames`）。[P 実験3]

### 「観測できなかった」の3分類【決定】[H §5]

1. 案Aの実装不足
2. MV3の構造的限界
3. ブラウザを通らない外縁（サーバー側スキミング）

## 5. 検体設計【決定】[H §4]

**2026-10-24 の変更（C7）:** 検体は、3軸OFATの約9個から、**1つのスキマーモデル**に変更した。ベースは [RQ] のグループ定義、カスタマイズも可。どのグループを基にするか等は未決（Q10、U-21）。以下の3軸の記述は変更前で、スキマーモデルを設計する際の参考として残す。報告書の整理は `literature/riskiq_inside_magecart_2018.md`。

- RiskIQ の7グループは網羅せず、観測に効く3軸で再現する。
  - 軸1 送信手段: fetch / XHR / 画像GET / sendBeacon / WebSocket
  - 軸2 送信先: 攻撃者サーバー / 乗っ取り実在サイト風 / 正規サービス装い
  - 軸3 符号化: 平文 / Base64 / 時刻・乱数利用の暗号化
- OFAT: 基準（fetch × 攻撃者 × 平文）から一軸ずつ変える。基準1 + 軸1を4 + 軸2を2 + 軸3を2 = 9個前後。
- 公開レポート（Sansec/Akamai等）の挙動を自作する。本物の攻撃コードは使わない。
- 対解析機能（サンドボックス検知等）は3軸に含めず、観測の失敗要因として別枠で扱う。
- 【未確認】軸3の扱いは [S P23]（難読化等はスコープ外）と食い違う。`analysis/open_issues.md` E-2。
- 参考（[S P23]）: RiskIQ の分類は7グループで、主な要素は「送信手段（POST/GET）」「決済画面・フォームの識別ロジック」「フォームデータの収集・操作手法」「難読化・対解析・隠蔽技術」。このうち [H §4] の3軸に対応する要素と、対応しない要素（識別ロジック・収集手法）の扱いは、資料に明記がない。

## 6. 評価基準

- 【決定】評価の重心は検知器の精度（precision/recall）ではなく、観測・判定できる範囲の境界。[H §1, §9]
- 観測可能性マップ: 行は決済方式（× 正規/悪性）、列は「送信発生 / 宛先 / 送信内容 / 判定（正規/悪性）」（= L1〜L4）。[S P12] 現状の実測は L1〜L3 を ○/× で記録。○/△/× の記述は [P 未実施] の「到達率（○△×の量的判定）」にあるが、△ の基準は【未確認】。
- 【未確認】L4 の「境界の定量」の方法（指標、データ数）は資料に具体化されていない。

## 7. 前提条件・制約（PoC）

- 【観測】別オリジンは、ホスト名とポートの差で再現した（`localhost:8080` が加盟店、`127.0.0.1:8081` がPSP）。eTLD+1 の差や証明書は扱っていない。[P]
- テストPAN: PoC では `4111111111111111`（Luhn妥当）。[P] [H §7] の例示は 4242 4242 4242 4242（公開テスト番号）。
- 「L3○」は平文送信に限った結論。難読化時は未検証。[P]
- 単発の成否のみ。反復・到達率は未実施。[P]
- 送信手段は `fetch` のみ。XHR / sendBeacon / form.submit は未対応。[P]

## 8. MV3で変わった点（Bower の方式が不成立になる根拠）

【文献・外部仕様】本リポジトリに一次資料なし。[H §10] の記述に基づく。

- webRequestBlocking の廃止 → 一般拡張は通信を止められない。declarativeNetRequest は送信 body の中身を条件にできない。
- 非ブロッキングの webRequest は残る → 観測は可能（案Bの根拠）。requestBody で中身も読める。
- background が Service Worker 化 → 使い捨て。観測結果は永続領域へ逐次保存が必要。
- content script の world を manifest で宣言可能（Chrome 111以降）→ 案A（MAIN world）成立の根拠。

【未確認】MV2 の完全廃止時期（[S P15] は「2026年8月」）も一次資料がない。
