# 観測モデル・用語・評価基準

出典の略称は `README.md` を参照。決定の一覧と理由は `research_decisions.md`。実験の設計とテストは `experiment_spec.md`。

## 1. 用語

| 用語 | 定義 | 出典 |
|---|---|---|
| スキマー | 正規ECサイトに不正に埋め込まれ、入力されたカード情報を攻撃者サーバーへ送る JavaScript。別名 Magecart / formjacking | [H §2] |
| 取得部 | スキマーの部品。カード情報を手に入れる。入力欄を読む型と、偽フォームに置換する型がある。EC型ごとに変える（D23） | 研究者の承認（2026-11-02） |
| 送信部 | スキマーの部品。手に入れた情報を送る。送信手段・宛先・符号化を決める。全モデルで共通にする（D23） | 研究者の承認（2026-11-02） |
| PSP | 決済代行会社（例: Stripe, GMO）。カード情報を加盟店に代わって扱う | [H §2] |
| 加盟店 | PSP を使っているEC店舗 | [S P16] |
| PAN | カード番号（Primary Account Number） | [H §2] |
| MV3 | Manifest V3。Chrome拡張の現行仕様。通信のブロック能力が削られ、観測が中心 | [H §2] |
| 案A | ページ内で JavaScript の送信命令（fetch等）を横取りして中身を見る拡張方式 | [H §2] |
| 案B | webRequest でページ外側からネットワーク通信を監視する拡張方式 | [H §2] |
| 正規宛先 | カード情報が送られるべき宛先。送信ごとに1つ。EC型ごとに設定する（D17） | 研究者の指示（2026-11-02） |
| sinkhole | 自作の、攻撃者サーバーの代わりの受け手。スキマーの送信先。自PC内のみ（D13） | [H §7] |
| SOP | 同一オリジンポリシー。ページ JS 同士を隔てる仕組み | [S P18], [P 実験1] |
| 正解記録 | 観測装置と独立した記録（サーバー受信ログ + CDP）。測定対象ではなく照合用（D18） | [H §5], [P 実験1] |
| 識別子 | 試行ごとに変わる文字列。PAN以外の欄（カード名義など）に入れ、ログの照合と経路の漏れの検出に使う（D20） | 研究者の承認（2026-11-02） |
| 測定対象外 | 測定しないと決めたもの（例: リダイレクト型の悪性ケース）。「観測できなかった」とは区別する（D16） | 研究者の指示（2026-11-02） |
| overturn | [H §8] に「案Bのoverturn（iframe型でもL3観測可）」とある語。定義は資料にない。意味は【未確認】 | [H §8] |

## 2. 観測レベル（L1〜L4）

| レベル | 内容 | PoC での実装 |
|---|---|---|
| L1 発生 | カード送信が起きたことを検知。本実験では、本文を使わず、拡張機能が POST 送信を1件記録したかで判定する（D50） | 案A・案B |
| L2 宛先 | 送信先を特定 | 案A・案B |
| L3 内容 | 送信内容からPANを復元 | 案A・案B。判定は素朴な `includes` のみ [P] |
| L4 判定 | 送信先が正規宛先かを照合し、正常/危険を判定。本実験では2方式（D51）。**L4a**: 正規宛先を試行ごとの設定として拡張機能に渡す。**L4b**: 渡さず、見える情報だけで判定する（送信元フレームのオリジンと宛先のオリジンが同じなら allow、違えば deny） | 案A・案Bとも実装・実施済み（E15〜E18。実 Stripe 版は E19〜E26）。PoC では PSP 宛を許可する照合（旧称 allowlist）で、案BのみL4を実施した [P] |

【決定】○/△/× は一致数 / 試行数から導く要約（○ = 全試行で一致、× = 全試行で不一致、△ = その中間）。L3 の「復元成功」= 取り出したカード番号が正解記録と完全一致。L4 の成功 = 判定が正解（正規は allow、悪性は deny）と一致。一次の結果は件数（D37、`experiment_spec.md` §5.3）。反復回数は D21。

## 3. 決済方式の分類

【決定】PCI の5型を決済方式の分類とする（D5）。カード情報の経路は [PCI §2.1〜2.5] の記述。

| 型 | PCI | 入力欄の場所 | カード情報の経路【文献】 | 正規宛先【仮説】 | 悪性ケース |
|---|---|---|---|---|---|
| URLリダイレクト | §2.1, p.8-9 | PSPのページ | ブラウザ→PSP。加盟店は扱わない | PSP | **測定対象外**（D16）。正規ケースのみ |
| iFrame | §2.2, p.10-12 | 加盟店ページ内の、PSPのiFrame | ブラウザ→PSP。SOP に依存して加盟店の JS から隔てる | PSP | 対象 |
| ダイレクトポスト | §2.3, p.13-14 | 加盟店が生成したフォーム（加盟店ページ） | ブラウザ→PSP直接。加盟店サーバーを通らない | PSP | 対象 |
| JavaScriptフォーム | §2.4, p.15-17 | PSPのJSが加盟店ページ内に作るフォーム | ブラウザ→PSP直接 | PSP | 対象 |
| API | §2.5, p.17-18 | 加盟店ページのフォーム | ブラウザ→加盟店サーバー→PSP | 加盟店サーバー（ブラウザからの送信） | 対象。加盟店サーバー→PSPの区間はブラウザ外（外縁③） |

- 「正規宛先」の列は、PCI の経路からの導出で、実測ではない。型ごとの確定は `experiment_spec.md`。
- 【決定】PCI §2 冒頭の「iFrame以外のタグによる埋め込み」「加盟店ゲートウェイ + 第三者の埋め込みAPI」は範囲外（測定対象外）。本文は未読で、観測結果が既存の型と同じかは【未確認】（D43）。
- 【観測】PoC の2方式は、直接送信型（トップから送信）、iframeホスト型（別オリジン iframe 内から送信）と呼ばれている。PCI の5型との対応は PoC の記録にない。[P] 本実験用の実装はまだ無い（2026-10-24、研究者の申告）。

## 4. 観測点

- 【決定】観測点は案A・案Bの2点。理由は作業量ではなく、「ページ内側の層（案A）と外側の層（案B）の代表」であること（D9）。[H §5]
- 計測器（CDP等）は3点目だが、案A・案Bの結果を照合する正解記録として使う。測定の列は2点のまま（D9、D18）。
- 案Aの横取りは、検体の送信手段と一致させる（D10）。[H §5]
- 【観測】案Aが成立する条件は MAIN world かつ iframe 内にも注入すること（`all_frames`）。[P 実験3]

### 「観測できなかった」の3分類と「測定対象外」【決定】

1. 案Aの実装不足
2. MV3の構造的限界
3. ブラウザを通らない外縁（サーバー側スキミング）

これらとは別に、測定しないと決めたものは「測定対象外」と書く（D11、D16）。

## 5. スキマーモデル【決定】

出典: D6、D15、D23（`research_decisions.md`）。RiskIQ 報告書の整理は `literature/riskiq_inside_magecart_2018.md`。

- 自作のスキマーを2種類（モデルX: 入力欄を読む、モデルY: 偽フォームに置換）作る（D26）。モデルは RiskIQ [RQ] に準拠する。本物の攻撃コードは使わない（D7）。
- スキマーを2つの部品に分ける（D23）。

| 部品 | 内容 | 変えるか |
|---|---|---|
| 取得部 | カード情報を手に入れる方法 | EC型ごとに変える |
| 送信部 | 送信手段、宛先、符号化 | 全モデルで共通 |

- ECは最も簡素な最低要件で設計し、それに最適なスキマーを選んで埋め込む。「最適」の基準は、実験の前に文章で固定する（D15）。
- 【決定】型ごとの当てはめ（D31）: iFrame型 = モデルY（偽フォーム置換）、ダイレクトポスト・JavaScriptフォーム・API = モデルX（入力欄を読む）、リダイレクト型 = 悪性ケースなし。理由: 別オリジンの iFrame の中の入力欄は、親ページの JS から読めない（SOP。[P 実験1]）。選定基準は D32。【観測】JavaScriptフォームでは、モデルXが、自作の PSP の JS が作った入力欄を読めた（E11、F15。通常の DOM・平文・各1回。実在のPSPの JS では【未確認】）。
- RiskIQ 報告書の取得方法の違い【文献】（[RQ p.8-36]。コードの図は未読）: 入力欄の値を読む（Group 1、5、6、7）、決済事業者ごとのフィールドID一覧で判定（Group 3）、決済フォームを偽フォームに置換（Group 4）。
- 対解析機能は主要素に含めず、観測の失敗要因として別枠で扱う（D8）。具体案は未確定。
- 【決定】符号化: 送信部はプレーン（name=value）で送る（D30）。符号化したスキマーは未測定で、限界に書く（`experiment_spec.md` §10）。

## 6. 評価基準

- 【決定】評価の重心は検知器の精度（precision/recall）ではなく、観測・判定できる範囲の境界（D2、D14）。[H §1, §9]
- 観測可能性マップ: 行は決済方式（× 正規/悪性）、列は「送信発生 / 宛先 / 送信内容 / 判定（正規/悪性）」（= L1〜L4）。[S P12] リダイレクト型の悪性の行は「測定対象外」と書く（D16）。
- 試行は基本3回、食い違いが出た条件だけ10回（D21）。結果は「3/3で一致」のように書く。
- 現状（PoC）の実測は L1〜L3 を ○/× で記録。本実験では、件数を一次の結果とし、○/△/× は件数から導く（D37）。[P 未実施] の「到達率（○△×の量的判定）」に対応する。
- 【未確認】L4 の「境界の定量」の方法（指標、データ数）は資料に具体化されていない。

## 7. 前提条件・制約（PoC）

- 【観測】別オリジンは、ホスト名とポートの差で再現した（`localhost:8080` が加盟店、`127.0.0.1:8081` がPSP）。eTLD+1 の差や証明書は扱っていない。[P]
- テストPAN: PoC では `4111111111111111`（Luhn妥当）。[P] [H §7] の例示は 4242 4242 4242 4242（公開テスト番号）。
- 「L3○」は平文送信に限った結論。難読化時は未検証。[P]
- PoC は単発の成否のみ。[P]
- PoC の送信手段は `fetch` のみ。XHR / sendBeacon / form.submit は未対応。[P]

## 8. MV3で変わった点（Bower の方式が不成立になる根拠）

【文献・外部仕様】本リポジトリに一次資料なし。[H §10] の記述に基づく。

- webRequestBlocking の廃止 → 一般拡張は通信を止められない。declarativeNetRequest は送信 body の中身を条件にできない。
- 非ブロッキングの webRequest は残る → 観測は可能（案Bの根拠）。requestBody で中身も読める。
- background が Service Worker 化 → 使い捨て。観測結果は永続領域へ逐次保存が必要。
- content script の world を manifest で宣言可能（Chrome 111以降）→ 案A（MAIN world）成立の根拠。

【未確認】MV2 の完全廃止時期（[S P15] は「2026年8月」）も一次資料がない。
