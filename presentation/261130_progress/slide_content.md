## A. 振り返り（前回のスライドを引用しながら）

### A1. 背景と問い

- **Webスキミング**（別名 Magecart）：正規の EC サイトに仕込まれた**スキマー**（悪意のある JavaScript）が、入力されたカード情報を攻撃者のサーバーへも送る
  → 消費者は、正規のサイトで買い物をしていても被害を受ける
- 防御の非対称
  - EC 側：脆弱性対策、多要素認証、定期監査など
  - 消費者側：「信頼できないサイトを避ける」が主
  → 消費者の手元（ブラウザ）で、何が見えるのかが分かっていない
- **問い**：消費者が入れられるブラウザ拡張機能で、カード情報の送信をどこまで観測できるか
- 図の候補：顧客 → 正規フォーム → **正規送信** → PSP（正規宛先）／スキマー → **悪性送信** → 攻撃者サーバー
- 1回だけ説明する語：Webスキミング、スキマー、正規送信・悪性送信、PSP（決済代行会社。カード情報を加盟店＝PSP を使う EC 店舗に代わって扱う）
- 必要な※注: Stripe（例として PSP の例に出す場合）

### A2. 先行研究と課題

- **Bower（2019）**：MV2 の拡張機能で、スキマーを検出・阻止
  - 送信の本文を **webRequest** で監視
  - ページ内へ **content script** を入れて、内側から観測
- 課題
  1. **MV2** の環境の研究。**MV3** で、同じ手法が使えるか分からない
  2. EC の実装形式（入力欄の場所・宛先・フレーム）を区別していない
     → 形式ごとの観測の限界が分かっていない
- Bower 自身が明記した未対応：置換 Base64、暗号化＋乱数化、偽陰性（【文献】）
- 必要な※注: webRequest、content script、Manifest V3（MV3）

### A3. 研究課題

- 主問い：MV3 の拡張機能は、EC の5型で、カード情報の送信をどこまで観測できるか
- 観測レベル（L1〜L4）：**L1 発生**（送信が起きた）／**L2 宛先**／**L3 内容**（カード番号の復元）／**L4 判定**（正規か悪性か）
- 正規宛先：カード情報が送られるべき宛先
- 必要な※注: Manifest V3（MV3）

## B. やっていたこと

### B1. 全体像

- 必要な※注: PCI DSS、Stripe

### B2. 実験環境

- **自作の EC を5型で用意**（PCI DSS の分類）。最低要件だけの簡素な作り
- **実行環境**（すべて1台の PC の中。外部に出さない）
  - OS：WSL2（Windows 上の Linux）。コードは Node.js と素の JavaScript
  - ブラウザ：Playwright が同梱する **Chromium**（版を固定。自動更新で変わらない）
    - フル版の Chromium を指定して起動する。既定の簡易ヘッドレスのブラウザでは、拡張機能が読み込まれず、別オリジンの iFrame が別プロセスにならなかったため【観測】
  - 3つのサーバーを同じ PC の上で動かし、別サイトとして扱う
    - 加盟店 `merchant.localhost:8080`／自作のダミー PSP `psp.localhost:8081`／攻撃者サーバー役の受け手（**sinkhole**）`sinkhole.localhost:8082`
- **1回の試行の流れ（全自動）**
  1. 顧客役のスクリプトが、決済ページでテストカードを入力する（名義欄に、その試行だけの識別子を入れる）
  2. 正規送信が PSP へ届く。悪性の条件では、スキマーが sinkhole へも送る
  3. 拡張機能が、見えた送信を記録する（ページ内方式と webRequest方式は、別々の試行で測る）
  4. 試行の後、測定スクリプトが、サーバー側の受信ログとブラウザ側の通信記録（**CDP**）を、拡張機能の記録と照合する
  5. 毎試行、自動チェックをする：受信内容が入力と全項目一致／送信先が `localhost` と `*.localhost` のみ／カード番号が公開テスト番号のみ。不合格の試行は無効として理由を記録し、直して再実行する
  6. 記録は、試行ごとのフォルダに保存する
- この環境の限界：別サイトは、ホスト名とポートの違いで再現している（登録可能ドメインの違いや証明書は扱わない）。Chromium 158（WSL2）のみで確認

| EC型 | カード入力欄の場所 | 正規送信の宛先 |
|---|---|---|
| URLリダイレクト | PSP のページ | PSP |
| iFrame | 加盟店ページ内の、PSP の iFrame | PSP |
| ダイレクトポスト | 加盟店ページのフォーム | PSP（加盟店サーバーを通らない） |
| JavaScriptフォーム | PSP の JS が、加盟店ページ内に作るフォーム | PSP |
| API | 加盟店ページのフォーム | 加盟店サーバー → PSP |

→ 型によって、スキマーが入力欄を読めるか、正規宛先がどこか、が変わる
- 必要な※注: PCI DSS、Playwright、Chromium、CDP

### B3. スキマーと観測の仕組み

- **スキマー（自作・2種類）**：RiskIQ（Webスキミングを調査するセキュリティ企業）の公開報告書（2018）に準拠。本物の攻撃コードは使わない
  - **取得部**（カード情報を手に入れる）：読み取り型 = 入力欄を読む／偽フォーム型 = 偽フォームに置き換える
  - **送信部**（送る）：全スキマーで共通（平文、`fetch`、宛先は sinkhole）
  → 取得部だけを変え、送信部をそろえる理由：結果の差の原因を、EC型の違いに絞るため
- **EC型ごとの割り当てと、その理由**（決め手は「入力欄をスキマーが読めるか」）

| EC型 | 割り当て | 理由 |
|---|---|---|
| ダイレクトポスト | 読み取り型 | 入力欄が加盟店ページの中にあり、ページの JavaScript から読める |
| JavaScriptフォーム | 読み取り型 | PSP の JS が作る入力欄だが、加盟店ページの中の通常の要素なので、読める（自作の PSP の JS で確認済み） |
| API | 読み取り型 | 入力欄が加盟店ページの中にあり、読める |
| iFrame | 偽フォーム型 | 入力欄が別オリジンの iFrame の中にあり、親ページの JavaScript から読めない（同一オリジンポリシー）。そこで iFrame を偽フォームに置き換えて入力させ、その後、本物の iFrame を出し直す |
| URLリダイレクト | なし（悪性は測定対象外） | 入力欄は PSP のページにあり、加盟店ページに仕込んだスキマーの対象にならない。遷移先をすり替える悪性は、他の型のスキマーと別の挙動になるため、扱わない |

- 割り当ての基準（実験の前に固定）：拡張機能なしの状態で、悪性送信が sinkhole に届くスキマーを使う。**拡張機能の観測結果を見て、スキマーを選び直さない**（観測しやすいものを選んだ、という恣意性を避けるため）
- **観測する側（MV3 の拡張機能）**
  - **ページ内方式**：ページ内で、送信命令（`fetch` など）を横取りして中身を見る（content script）
  - **webRequest方式**：webRequest で、ページの外側から通信を監視
- **正解記録**：拡張機能と独立に、サーバー側の受信ログと、ブラウザ側の通信記録の2本で「実際に何が送られたか」を取り、拡張機能の結果と照合
- 必要な※注: content script、webRequest、Manifest V3（MV3）

### B4. 測定の条件と評価

- **条件**：5型 × 正規／悪性 × ページ内方式／webRequest方式 ＝ **18条件**（リダイレクト型の悪性は測定対象外）、**各3回 ＝ 54試行**
  - 別に、拡張機能なしの基準試行（9条件）で、EC とスキマーが想定どおり動くことを確認
- **結果の表し方**：一致数／試行数（例: 3/3）。全一致 = ○、全不一致 = ×、その中間 = △
- 観測できなかったときは、原因を3つに分ける：ページ内方式の実装不足 / MV3 の構造的限界 / ブラウザを通らない通信
- **安全**：自 PC 内のみ。送信先は自作サーバーのみ。公開テスト用のカード番号のみ
- 必要な※注: Manifest V3（MV3）

### B5. 試行錯誤（設計の見直し）

1. **最小構成**：自作の EC・ダミー PSP・スキマーで、5型を一通り測定
2. **実 Stripe へ**：自作ダミー PSP だけでなく、実在の決済の通信でも測る（別枠で追加。11/17）
   - 理由（研究者）：様々な条件で、観測性がどこでどう変わるかを明確にしたい
3. **判定（L4）の見直し**
   - 宛先を渡す判定：正規宛先を、実験側が拡張機能へ渡す（答えを渡した状態）
   - 宛先を渡さない判定：渡さず、拡張機能が見える情報だけで判定（11/17 に追加）
   - 判定ルールの比較：5つのルールを、実行前に固定して採点（11/22）
   - 理由：宛先を渡す判定は答えを渡した結果で、実際の拡張機能の状況を表さない
- 必要な※注: Stripe

## C. 結果

凡例（ページ内方式・webRequest方式 を出すブロックに添える）：ページ内方式 = ページ内で横取り／webRequest方式 = webRequest で外側から監視。必要な※注: content script、webRequest。

### C1. 5型の観測（L1〜L3）

**条件**：自作 EC・自作スキマー・平文・`fetch`・公開テスト番号・各3回

- 【観測】ページ内方式・webRequest方式 とも、ブラウザを通る送信（正規・悪性）は、5型すべてで、L1（発生）〜L3（内容）が正解記録と **3/3 で一致**（各27試行）
- 【観測】別オリジンの iFrame 内からの送信も、両案とも記録
- 【観測】**ページ内方式 とwebRequest方式 の間に、差は出なかった**
- 【観測】API 型の「加盟店サーバー → PSP」の送信は、ページ内方式・webRequest方式 とも見えなかった
  → ブラウザを通らない通信であり、観測の失敗ではない

### C2. 判定（L4）：正規宛先を渡すか、渡さないか

**条件**：自作 EC・自作スキマー・平文・`fetch`・各3回。宛先を渡さない判定のルールは1つ

宛先を渡さない判定のルール：送信元のフレームの**オリジン**（URL のスキーム・ホスト・ポートの組）と宛先のオリジンが同じなら allow（正規）、違えば deny（悪性）

| EC型 | 宛先を渡す判定 | 宛先を渡さない判定（正規送信） | 宛先を渡さない判定（悪性送信） |
|---|---|---|---|
| URLリダイレクト | 3/3 ○ | 3/3 ○ | 測定対象外 |
| iFrame | 3/3 ○ | 3/3 ○ | 3/3 ○ |
| ダイレクトポスト | 3/3 ○ | **0/3 ×** | 3/3 ○ |
| JavaScriptフォーム | 3/3 ○ | **0/3 ×** | 3/3 ○ |
| API | 3/3 ○ | 3/3 ○ | 3/3 ○ |

- 【観測】ダイレクトポスト型・JavaScriptフォーム型では、正規送信を、ページ内方式・webRequest方式 とも deny と**誤判定**した
- 【観測】この2型では、正規送信と悪性送信の特徴（宛先の名前を除く）が、全試行で同一だった
- 【解釈】この2型では、宛先の名前の知識がないと区別できない
- 注意：宛先を渡す判定が全て○なのは、答えを実験側が渡した結果

### C3. 実 Stripe

**条件**：自作の加盟店 ＋ Stripe（Card Element＝Stripe 提供のカード入力部品。別オリジンの iFrame で表示）のテストモード・平文・公開テスト番号・Stripe 1社・各3回

- 【観測】カード送信は、`api.stripe.com` への `fetch` の POST が1件（送信元は Stripe の iFrame）。ほかに、**カード番号を含まない POST が、1試行あたり約25〜27件**
- 【観測】ページ内方式・webRequest方式 とも、カード送信を L1〜L3、宛先を渡す判定 で 3/3 観測。ほかの POST も全て観測
  → 通信の数が多くても、**観測は壁にならなかった**
- 【観測】**宛先を渡さない判定は、正規送信を 0/3 で誤判定**（送信元と宛先のオリジンが違う）
  → 壁は、「どれが正規か」の判定
- 【観測】ページ内方式 が `fetch` のみだと、XHR の POST 3件（番号なし）を毎試行見逃した。XHR の横取りを足すと0件
  → 実装不足であり、MV3 の限界ではない
- 【観測】Card Element の iFrame は、親ページから読めなかった
  → 入力欄を読むスキマーは成立しない。**取得を伴う悪性は測定対象外**。代わりに、取得なしの模擬送信（sinkhole 宛て）を測定：観測は3/3 ○、宛先を渡さない判定は正規も悪性も deny で区別できず
- 必要な※注: Stripe

### C4. 判定ルールの比較

**問い**：宛先の知識なしで、見える情報だけで、正規送信と悪性送信を区別できるか
**条件**：既存ログの再評価。5ルールは実行前に固定。自作 EC＋実 Stripe・各3回

| ルール | 内容 | 結果 |
|---|---|---|
| 同一オリジン | 送信元と宛先が同じオリジンなら allow（= 宛先を渡さない判定） | ダイレクトポスト型・JavaScriptフォーム型・実 Stripe で、正規を誤判定 |
| 決済事業者の一覧 | 既知の決済事業者の一覧にあれば allow | API 型だけ誤判定（正規の宛先が加盟店） |
| トップページ比較 | トップページのオリジンと宛先を比べる | API 型以外の全型で、正規を誤判定 |
| パスの語 | URL のパスに決済関連の語があれば allow | 全型で正解。ただし、検体のパスは実装者の選択で、攻撃者は回避できる |
| 複数宛先 | 同一の決済操作で、カード番号が複数の宛先に出たら deny | 悪性を全型で deny。ただし同じ試行の正規送信も deny |

- 【観測】**宛先の知識を使わず、全型で正解になるルールはなかった**
- 【解釈】決済事業者の一覧・パスの語の正解は、宛先・パスの知識を使った結果。複数宛先は「2か所に出た」ことの検出で、どちらが悪性かは区別できない
- ページ内方式 とwebRequest方式 の差はなかった

## D. 考察

### D1. 観測の能力と、判定の壁

- 【解釈】Bower が MV2 で使った**観測の手法**（webRequest、content script）は、MV3 でも**観測の用途では**有効だった
  - 5型・ページ内方式・webRequest方式・実 Stripe で、L1〜L3 まで観測できた
  - 本研究は MV2 を測っていない。MV2 との実測の比較ではない
- 【文献】MV3 では、一般の拡張機能が通信を止める権限（webRequest のブロック）が外された。**通信を止められるか**は、本研究では測っていない（Chrome 公式での確認は【未確認】）
- 【解釈】課題は観測ではなく**判定**：正規送信と悪性送信の区別
  - 正規宛先を知っていれば区別できる（宛先を渡す判定）
  - 知らないと、2型（ダイレクトポスト、JavaScriptフォーム）と実 Stripe で区別できない（宛先を渡さない判定）
  - 通信が多くても観測は成立。判定の難しさは、正規送信の形が悪性送信と同じことから来た
- 必要な※注: webRequest、content script、Manifest V3（MV3）、Stripe

### D2. 型による違い

- 【観測】宛先を渡さない判定の判定は、型で差が出た
  - 区別できた：iFrame、API、URLリダイレクト
  - 区別できなかった：ダイレクトポスト、JavaScriptフォーム
- 【解釈】理由：正規の送信が、PSP 自身の画面（iFrame、リダイレクト）か、加盟店自身（API）に向かう型は、悪性送信と形が違う。加盟店のページから PSP へ直接送る型は、悪性送信と形が同じ
- **未解決の問い（【仮説】。未検証）**：PSP を通さない型は、通信が単純で判定しやすいが、スキマーも仕込みやすいか
  - 取得部：入力欄を読む読み取り型は、ダイレクトポスト・JavaScriptフォーム・API で成立。iFrame は、読めず、偽フォームへの置き換えが必要だった
  - API 型は、判定も取得も容易。iFrame 型は、判定は容易だが、取得に別の方法が要る
  → 「判定しやすい型ほど仕込みやすい」とは、今のデータでは言えない。型ごとの整理は今後

## E. 限界

- 自作 EC・自作スキマー・平文（符号化なし）・主に `fetch`・各3回。「常に観測できる」とは言えない
- 実 Stripe は1社・テストモード。取得を伴う悪性は測っていない
- 宛先を渡す判定は、正規宛先を実験側が渡した結果。宛先を渡さない判定 とルール比較は、ルールが1つ・5つだけ
- 検知率・誤検知率など、**有効性の指標は測っていない**。「対策として有効」とは言わない
- 実在のスキマー、実在の EC、符号化・難読化は未検証
