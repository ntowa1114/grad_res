# ③ 気づいたこと・考えていたこと（6:00）

## S9. 見直し：観測できるだけでは足りない → 判定を2通りに分けた（0:50）

- 気づき：観測できても、**どれが悪性かを区別できなければ、消費者は使えない**
- 判定（L4）を2通りに分けた
  - **宛先を渡す判定**：正規宛先を、実験側が拡張機能へ渡す（答えを渡した状態）
  - **宛先を渡さない判定**：拡張機能が見える情報だけで判定。ルールは1つ：送信元のフレームの**オリジン**（`https://js.stripe.com` のような、スキーム・ホスト・ポートの組）と宛先のオリジンが同じなら allow（正規）、違えば deny（悪性）
- 前者が全部 ○ になるのは、答えを渡したから。実際の状況に近いのは後者

## S10. 結果②：判定は、型によって差が出た（1:00）

**条件**：自作 EC・自作スキマー・平文・`fetch`・各3回。渡さない判定のルールは1つ（同一オリジン）

| EC型 | 宛先を渡す | 渡さない（正規送信） | 渡さない（悪性送信） |
|---|---|---|---|
| URLリダイレクト | 3/3 ○ | 3/3 ○ | 測定対象外 |
| iFrame | 3/3 ○ | 3/3 ○ | 3/3 ○ |
| ダイレクトポスト | 3/3 ○ | **0/3 ×** | 3/3 ○ |
| JavaScriptフォーム | 3/3 ○ | **0/3 ×** | 3/3 ○ |
| API | 3/3 ○ | 3/3 ○ | 3/3 ○ |

- 【観測】ダイレクトポスト型・JavaScriptフォーム型は、正規送信を、2方式とも **deny と誤判定**
- 【観測】この2型では、正規送信と悪性送信の特徴（宛先の名前を除く）が、全試行で同一
- 【解釈】この2型は、宛先の名前の知識がないと区別できない
- ※ここで聴衆に「iFrame 型は ○ だが、本当にそうか？」と思わせておき、S12 で回収する

## S11. 実 Stripe では、通信が約26件（0:50）

**条件**：自作の加盟店 ＋ 実 Stripe（Card Element。別オリジンの iFrame）のテストモード・平文・公開テスト番号・各3回

- 【観測】カード送信は、`api.stripe.com` への POST が1件。ほかに、**カード番号を含まない POST が、1試行で約25〜27件**
- 【観測】2方式とも、カード送信を L1〜L3 で 3/3 観測。ほかの POST も全て観測 → 通信が多くても、**観測は壁にならなかった**
- 【観測】ページ内方式が `fetch` だけだと、XHR の POST 3件（カード番号なし）を毎試行見逃した。XHR を足すと 0 件
  → 【解釈】実装不足であり、MV3 の限界ではない
- ※Stripe

## S12. 実 Stripe では、判定が ×：iFrame 型の ○ はなぜ崩れたか（1:20）

**条件**：S10・S11 と同じ

- 【観測】渡さない判定は、実 Stripe の正規送信を **0/3 で誤判定**
- 【観測】オリジンの組を比べると：

| | 送信元のオリジン | 宛先のオリジン | 同じか | 判定 |
|---|---|---|---|---|
| 自作の iFrame 型 | `psp.localhost:8081`（iFrame のページ） | `psp.localhost:8081`（受け口） | 同じ | allow（○） |
| 実 Stripe（iFrame） | `js.stripe.com` | `api.stripe.com` | 違う | deny（×） |

- 【解釈】自作 PSP は、iFrame と受け口を**同じオリジン**に置いた。実 Stripe は別のホストに分けている。同じ iFrame 型でも、**判定の結果は PSP の作り方で変わる**
  → S10 の iFrame 型の ○ は、「iFrame 型だから判定しやすい」ではなく、「自作 PSP の構成だと同一オリジンになる」結果
- 【観測】取得なしの模擬送信（sinkhole 宛て）も測定：観測は 3/3 ○。渡さない判定は、正規も悪性も deny で、**区別できず**
- ※Stripe の Card Element は、親ページから中身を読めなかった（`contentDocument` が `null`）。入力欄を読むスキマーは成立しないので、取得を伴う悪性は測定対象外

## S13. 他のルールなら区別できるか（1:00）

**問い**：宛先の知識なしで、見える情報だけで、正規送信と悪性送信を区別できるか
**条件**：既存ログの再評価。5ルールは実行前に固定。自作 EC＋実 Stripe・各3回

| ルール（短縮） | 結果 |
|---|---|
| 同一オリジン（S9 のルール） | ダイレクトポスト・JSフォーム・実 Stripe で、正規を誤判定 |
| トップページ比較 | API 型以外の全型で、正規を誤判定 |
| 決済事業者の一覧 | API 型だけ誤判定（正規宛先が加盟店） |
| URL のパスの語 | 全型で正解。ただし、検体のパスは実装者の選択で、攻撃者は回避できる |
| 複数宛先（カード番号が複数の宛先に出たら deny） | 悪性は全型で deny。ただし、同じ試行の正規送信も deny |

- 【観測】**宛先の知識を使わず、全型で正解になるルールはなかった**
- 【解釈】一覧とパスの語の正解は、宛先・パスの知識を使った結果。複数宛先は「2か所に出た」ことの検出で、どちらが悪性かは区別できない
- 2方式の差はなかった（※詳細は付録 D）

## S14. 気づきのまとめ（1:00）

- 【解釈】課題は**観測ではなく判定**
  - 観測：5型・2方式・実 Stripe で L1〜L3 まで成立。通信が多くても、成立した
  - 判定：正規宛先を知らないと、区別できない型・PSP がある
- 【解釈】判定のしやすさは、「型」では決まらない。**正規送信の送信元と宛先が、同じオリジンか**で決まる（S12）
  - 型だけで見ると、API 型は判定しやすい（宛先が加盟店で同一オリジン）。ダイレクトポスト型・JavaScriptフォーム型は判定しにくい
- **未解決の問い（【仮説】。未検証）**：PSP を通さない型（API 型など）は通信が単純で判定しやすいが、スキマーも仕込みやすいのではないか
  - 今のデータでは「判定しやすい型ほど仕込みやすい」とは言えない。型ごとの整理は今後
- 〔小休止〕「観測は思ったより簡単。難しいのは、どれが悪い通信かを決めること」と一言で締める

### B. スキマーの割り当てと理由（S7 の詳細）

| EC型 | 割り当て | 理由 |
|---|---|---|
| ダイレクトポスト | 読み取り型 | 入力欄が加盟店ページの中にあり、ページの JavaScript から読める |
| JavaScriptフォーム | 読み取り型 | PSP の JS が作る入力欄だが、加盟店ページの中の通常の要素なので読める（自作 PSP の JS で確認） |
| API | 読み取り型 | 入力欄が加盟店ページの中にあり、読める |
| iFrame | 偽フォーム型 | 入力欄が別オリジンの iFrame の中で、親ページから読めない（同一オリジンポリシー）。iFrame を偽フォームに置き換えて入力させ、その後、本物の iFrame を出し直す |
| URLリダイレクト | なし（悪性は測定対象外） | 入力欄は PSP のページにあり、加盟店ページに仕込んだスキマーの対象にならない |

- 送信部は全スキマーで共通（平文、`fetch`、宛先は sinkhole）。取得部だけを変え、結果の差の原因を EC 型の違いに絞る
- 割り当ての基準：拡張機能なしで、悪性送信が sinkhole に届くスキマーを使う

### C. 実験環境の詳細（S6 の詳細）

- WSL2、Node.js、素の JavaScript、Playwright 同梱の Chromium 158（版を固定）。フル版の Chromium を指定する（既定の簡易ヘッドレスでは、拡張機能が読み込まれず、別オリジンの iFrame が別プロセスにならなかった【観測】）
- `merchant.localhost:8080`／`psp.localhost:8081`／`sinkhole.localhost:8082`
- 毎試行の自動チェック：受信内容が入力と全項目一致／送信先が `localhost` と `*.localhost` のみ／カード番号が公開テスト番号のみ。不合格は無効として理由を記録し、直して再実行
- 別サイトは、ホスト名とポートの違いで再現（登録可能ドメインの違いや証明書は扱わない）
- 観測できなかったときの原因の3分類：ページ内方式の実装不足／MV3 の構造的限界／ブラウザを通らない通信

### D. 判定ルール比較の詳細（S13 の詳細）

- 同一オリジンはダイレクトポスト・JSフォーム・実 Stripe で 0/6（正規）、トップページ比較は API 型以外の全型で誤判定、決済事業者の一覧は API 型だけ誤判定、パスの語は全型で正解（検体依存）、複数宛先は悪性を全型で deny（正規も deny）。出典: F29、E27
